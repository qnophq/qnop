# ADR-0043: System-audit stream — generalising the audit trail beyond documents

- **Status:** Accepted
- **Date:** 2026-07-19
- **Deciders:** devtank42 (with Claude)

## Context

The `audit_event` log (issue #244, ADR-0011) has been **strictly per-document** since it shipped: `document_id` is `NOT NULL`, an `ON DELETE CASCADE` foreign key ties every row to a `document`, and the AUDITOR read surface (ADR-0042) reports the org-wide *document*-review trail. ADR-0042 drew an explicit boundary and **deferred** a "future system-audit stream (logins, settings, user admin — out of scope)".

The scheduler-jobs dashboard (issue #524) is the first feature that needs to record **org-level operator actions with no document**: an admin enabling/disabling a maintenance job, overriding its dry-run flag, or triggering a run-now. These are genuine audit events (who, what, old→new state) that belong in the same trail an AUDITOR/ADMIN already reads — but they have no `document_id`, so they cannot be written to `audit_event` as it stood.

Three options were considered (see issue #524 planning): (A) keep the events out of `audit_event`, recording operator state on the `scheduler_job` row only; (B) generalise `audit_event` with a nullable `document_id` and an explicit scope discriminator; (C) stand up a separate `system_audit_event` table and reader.

## Decision

**Option B.** `audit_event` becomes a two-scope trail:

- `document_id` is now **nullable**. The existing `fk_audit_event_document` (`ON DELETE CASCADE`) is unchanged — a null simply never participates in the cascade.
- A new **`scope`** column (`VARCHAR(16)`, `NOT NULL`, default `DOCUMENT`) discriminates `DOCUMENT` (the original per-document trail) from `SYSTEM` (org-level operator actions). The default backfills every pre-existing row correctly. A DB **check constraint** (`ck_audit_event_scope_document`) keeps the two in lock-step: a `DOCUMENT` row must have a document, a `SYSTEM` row must not — the discriminator and the foreign key can never disagree.
- `0011` shipped in v1.0.0, so this is a **new ALTER changeset** (`0016-audit-scope-schema.yaml`), not a fold into the released one.
- `AuditEvent.system(eventType, actorId, detail)` is the factory for `SYSTEM` rows; the existing 4-arg constructor keeps writing `DOCUMENT` rows unchanged, so none of the ~10 existing call sites move.
- The AUDITOR read surface (ADR-0042) is unchanged in shape: the org-wide list already returns every row; it now simply also returns `SYSTEM` rows, each carrying `scope` and a null `documentId`/`documentTitle`. Actor identity still resolves to the **real** display name (the ADR-0038 anonymity bypass for compliance applies identically). The `eventType` for scheduler actions is `scheduler.job.{enabled,dry_run,run_now}`.

## Consequences

- **Positive:** the deferred system-audit stream is now real, with one reader, one table, one exposure model — no parallel infrastructure (rejecting C). Compliance sees operator actions and document actions in one place. Future system events (settings changes, user admin) reuse `AuditEvent.system(...)` with no further schema change.
- **Negative / trade-offs:** `audit_event` is no longer "the document trail" — readers must not assume a non-null `document_id`. The check constraint adds a small write-time cost and must be kept in sync if scopes are ever added. Rejecting A means a schema change on a released table, but A would have split the audit story across two mechanisms, which is exactly what ADR-0042 anticipated folding back together.
- **Follow-up:** the AUDITOR UI (issue #466) may add an explicit scope filter/label; not required for the events to appear.

## Amendment (2026-11-11, issue #928): tamper evidence and resistance for `audit_event`

**Context.** `audit_event` was append-only by JPA mapping only (`updatable = false`, no delete path in code). The application's database role owns the schema, there was no trigger, no restricted grant and no integrity record, so anyone with SQL access or the database credentials could rewrite or remove history without trace. Document-scoped rows legitimately disappear with their document (`fk_audit_event_document ON DELETE CASCADE`; review deletion and purge leave a surviving SYSTEM event, ADR-0050), so "rows never disappear" is not the invariant to protect — "rows never disappear *except through that cascade*, and never change" is.

Options weighed: (1) an append-only trigger alone — cheap, but the schema owner can disable it, so it only stops mistakes and a compromised application layer; (2) a restricted application role — strong, but an operator choice the product cannot impose on every deployment; (3) a hash chain — makes changes *detectable* even for the schema owner, once its head is anchored outside the database; (4) an external append-only sink (log shipping, WORM storage) — the only control that survives a full database compromise, but infrastructure we cannot ship by default. They are complementary, so the decision layers them.

**Decision.** Migration `0040-audit-chain` adds:

1. **A global hash chain, sealed at commit.** New columns `chain_seq` (unique, gap-free at sealing), `prev_hash`, `row_hash`; a single-row `audit_chain_head` table holds the newest position and hash. A `DEFERRABLE INITIALLY DEFERRED` constraint trigger seals each inserted row at `COMMIT`: it locks the head row (`SELECT … FOR UPDATE`), sets `row_hash = hex(sha256(prev_hash ‖ canonical(row)))`, and advances the head. The canonical form is a versioned, length-prefixed encoding (`<utf8-byte-length>:<text>`, `~` for null) of id, scope, document id, event type, actor id, the normalised jsonb text of `detail`, and `created_at` as epoch microseconds — unambiguous and independent of session settings (time zone, date style). The genesis `prev_hash` is 64 zeros.
   - *Why commit time, not insert time.* The head lock serialises chain order across all instances; taken at `INSERT` it would be held from the first audit write to the end of the business transaction (which can include storage I/O) and invite lock-order deadlocks with the rows written afterwards. Taken at `COMMIT` it is held only for the commit itself, after every business statement has run, so it cannot deadlock and costs throughput only on the commit path (audit-writing commits serialise — fine at audit volumes, and the reason this is a row lock rather than a lock held across the request). Chain order is therefore commit order.
   - *Why the database computes the hash.* Every write path is covered — JPA, native SQL, the trigger-written tombstones below — without each service having to remember to call something, and the jsonb/timestamp normalisation the hash covers is exactly what is stored.
2. **Append-only guards.** A `BEFORE INSERT` trigger rejects rows that arrive with chain values already filled in (only the seal assigns them; a `CHECK` also forbids positions below 1) and rejects `audit.chain.pruned` rows not written by the tombstone trigger. A `BEFORE UPDATE` trigger rejects every update except the seal itself filling in the empty chain columns of an otherwise unchanged row from inside the sealing trigger. Deletes are sanctioned only for the document cascade, which is checked specifically rather than inferred from trigger depth: a `BEFORE DELETE` trigger on `document` records the ids being deleted in a transaction-local marker, and an `audit_event` row may go only if it is issued from inside a trigger, is a `DOCUMENT` row, its document is in that marker, *and* that document no longer exists (inside the referential action the parent row is already gone). Any other delete — direct, or issued from some other trigger or function — is rejected. `TRUNCATE` is not guarded (test cleanup relies on it); a truncation leaves the head pointing past the remaining rows and is reported by the verifier. All trigger functions pin `search_path` to the application schema with `pg_temp` last, so no session-local object can shadow a table inside them; the seal refuses to run outside `READ COMMITTED` with a clear error, and the migration refuses PostgreSQL < 14.
3. **Prune tombstones.** A statement-level `AFTER DELETE` trigger (transition table) re-checks the same sanction for every removed row — so disabling either the row guard or the tombstone writer alone does not open a silent delete path (the first still raises in the second; without the second the removal is an unexplained gap) — and records each cascade as an `audit.chain.pruned` SYSTEM event whose detail lists the affected document ids and every maximal run of consecutive removed positions as `{fromSeq, toSeq, prevHash, lastHash}`. The verifier bridges a hole in the chain only when a tombstone range covers it exactly, the range's `prevHash` is the hash of the surviving row before it, its `lastHash` is the `prevHash` of the surviving row after it, and the tombstone itself was sealed *after* the range; a second tombstone claiming an already-claimed start position is itself reported. Every document a tombstone names must also be explained by a `review.deleted` or `review.purged` SYSTEM event (the purge event now lists all purged ids, uncapped). A review deleted through the application therefore verifies clean; a row removed any other way, or a document deleted outside the review-deletion services, is reported. Tombstones are ordinary chained, AUDITOR-visible events, so purges stay visible in the compliance view.
4. **Verification** — `AuditChainVerifier` (plain Java) walks the chain in a single `REPEATABLE READ` snapshot, recomputing every hash with an *independent Java implementation* of the canonical form (`AuditChainHasher`; field lengths are UTF-8 byte counts on both sides), so redefining the SQL function cannot hide an altered column. It reports unsanctioned gaps, broken links, content mismatches, malformed or duplicate tombstones (parsed defensively — a bad payload is a finding, never an abort), unexplained prunes, a walk that does not end on the recorded head, rows that are unsealed or carry an impossible position, and a table row count that the walk does not account for. It runs as the catalogued scheduler job `auditChainVerify` (nightly, run-now from the scheduler dashboard, ADR-0045). An intact run logs the head position and hash (the external anchor, see below); a broken run logs at ERROR, writes an `audit.chain.broken` SYSTEM event with the located problems, fails the run on the dashboard, and sets the `qnop.audit.chain.intact` gauge to 0. A run that errors before reaching a verdict also reads as not intact, never as the previous result; after a restart the gauge falls back to the persisted outcome of the last run on any instance.
5. **Backfill.** The migration seals all pre-existing rows once, in `(created_at, id)` order, before the guards are installed. It runs row by row under the migration's table lock (writers wait for it) and rewrites every row once; run `VACUUM ANALYZE audit_event` afterwards on large trails. The changeset carries an explicit rollback that drops the guards and the chain.
6. **Restricted role and external shipping are documented, not imposed** — `docs/DEPLOYMENT.md` describes migrating as the schema owner from a separate one-off job and running the application as a role holding only `SELECT, INSERT` on `audit_event` (the sealing and tombstone functions are `SECURITY DEFINER`; referential cascades run as the table owner), and shipping the verifier's checkpoint log lines to an external store.

**Consequences.**

- *Prevents* (for a role that does not own the schema, i.e. with the restricted role): updates, deletes other than the review cascade, pre-sealed or forged-tombstone inserts, and disabling the triggers.
- *Detects* (also against the schema owner, as long as the chain is not recomputed forward): any change to a sealed row's content; any removal not covered by a well-formed tombstone; a cascade whose document deletion no review-deletion/purge event explains; rows inserted with the triggers bypassed (unsealed, impossible position, or unaccounted for); truncation; and a rewound head.
- *Does not prevent on its own:* whoever owns the schema (the application role in the default deployment) can disable the triggers, delete or edit rows, write matching tombstone and review-deletion events, and recompute every later hash. An unkeyed chain cannot stop that by itself; what catches it is comparing the current chain with a head checkpoint stored outside the database (the shipped log line — a rewritten chain no longer contains the earlier logged head at its logged position). Operators who need prevention run the restricted application role. A keyed (HMAC) chain with the key held outside the database was considered and deferred: it needs Java-side sealing (losing the "every write path is covered" property) and key management, for a gain the external checkpoint already provides.
- *Cost:* three columns and one row lock per audit-writing commit; verification is a full O(n) scan once a night (incremental checkpoints are a possible later optimisation). Audit writes must run under `READ COMMITTED` (enforced by the seal); every current writer uses that default.
- *Chain columns are not mapped on the JPA entity* — the application can neither read nor write them through Hibernate; they are read only by `AuditChainRepository`.

## Amendment (2026-11, #952): erasing users the audit trail names

**Context.** `audit_event.actor_id` references `qnop_user` with `ON DELETE RESTRICT`, SYSTEM-scope rows never cascade away, and detail payloads snapshot personal data (e.g. `team.*` events carry `userId` and `userName`). Since #948 a user who merely answered a team invitation is an audit actor, and #951 could only turn the failed delete into `409 USER_HAS_AUDIT_HISTORY`. An erasure request (GDPR Art. 17) could therefore not be fulfilled. The chain amendment above hashes `actor_id` and `detail`, so the personal data cannot simply be overwritten: any change is, by design, a content mismatch.

Options weighed: **(A)** a sanctioned, chain-verifiable redaction path that rewrites the personal data in place, keeps the chain columns, and records the redaction — including a hash of the redacted content — as its own chained event; **(B)** keep personal data out of the hash entirely — hash a stable pseudonymous key and resolve it through a mapping table that erasure simply deletes. B keeps every row fully verifiable after an erasure, but it changes the canonical form (a new format version, a second backfill of the whole chain) and every audit writer and reader. A is local to the database and the verifier. **Decision: A**; B stays a possible future direction (see below).

**Decision.** Migration `0042-audit-redaction`:

1. **Redaction columns** `redacted_at`, `redaction_id` and `actor_pseudonym` on `audit_event` (a check keeps the first two set together and allows a pseudonym only on a redacted row without actor). The JPA entity maps `redacted_at` and `actor_pseudonym` read-only; inserts that arrive with any of them set are rejected.
2. **One redaction path, triggered by account deletion.** A `BEFORE DELETE` trigger on `qnop_user` runs `audit_event_redact_user` (`SECURITY DEFINER`, `search_path` pinned, `EXECUTE` revoked from `PUBLIC`): a user leaves the trail exactly when — and only when — the account is deleted, by any path. Each erasure draws a fresh redaction id and a fresh pseudonym `erased-user:<random uuid>` (one per erasure; nothing derivable from the user).
3. **Authorisation by state the application cannot write.** The function records its parameters (user, redaction id, pseudonym, time, phase, and the one event it is about to write) in `audit_redaction_context`, a table keyed by `txid_current()` on which every privilege is revoked — from `PUBLIC` and from every role a default-privileges rule had granted it to — and clears it before returning. It must never be granted to the application role: a later blanket `GRANT … ON ALL TABLES` would do so, so re-run its `REVOKE` after one (trigger depth stays required, but the context is the second barrier). The guards read it through a read-only `SECURITY DEFINER` helper. Session settings (GUCs) authorise nothing: an earlier draft of this change armed the guard with a transaction-local GUC, which any session can set.
4. **Update guard, exact form only.** Besides the seal, `audit_event_reject_update` permits only a redaction, and only when (a) it runs inside a trigger (`pg_trigger_depth() > 1`; a direct `UPDATE`, or a direct call of the function, is depth 1), (b) the context for this transaction is in its `redact` phase, and (c) the new row is *exactly* the pseudonymised form of the old one for that context: `detail = audit_event_redact_detail(old detail, erased id, pseudonym)`; an actor equal to the erased user becomes NULL with the context's pseudonym, every other actor and pseudonym stay; `redaction_id` and `redacted_at` are the context's; id, scope, document, type, time and the chain columns are unchanged; and the row actually names the user. A row redacted before may be redacted again on the same terms — i.e. when it also names this second user (one row can name two erased users: the actor, and the subject in the detail). It then carries the latest redaction.
5. **Bounded walk.** `audit_event_redact_detail` stops recursing at nesting depth 32: from there, a subtree that contains the user's id anywhere becomes the fixed string `[erased: nested too deep]`, and any other subtree is kept. Any role that may append audit rows could otherwise write a detail deep enough to exhaust the stack inside the user-delete trigger and make that user undeletable for good (the row is append-only). The update guard and the content hash use the same function, so they admit and bind exactly the bounded result.
6. **What is pseudonymised.** In the rows whose `actor_id` is the user or whose detail contains the user's id: the actor; every detail string value that *is* the user's id (case-insensitive); and, inside an object whose `userId` is the user, the values of its name keys (`userName`, `username`, `name`, `displayName`, `userDisplayName`, `email`, `userEmail`) — the snapshot written next to the id, which can predate a rename. Nothing else: strings that merely equal the user's name elsewhere are *not* replaced, because names are user-chosen and matching them anywhere would let one user's name blank out unrelated audit content.
7. **The records.** The function writes, in the `record` phase and admitted by the insert guard only as exactly the event the context announces (`pg_trigger_depth() > 1` again):
   - an `audit.chain.redacted` SYSTEM event `{redactionId, rows: [{id, seq, rowHash, contentHash}], pendingRows}` — per redacted row its id, its position and original `row_hash` (both null for a row not sealed yet), and `contentHash = sha256(prev_hash ‖ canonical(row) ‖ redactionCanonical(pseudonym, redaction id, redacted_at))` over the *redacted* content (prev `''` for an unsealed row); `pendingRows` counts the unsealed entries. No personal data, not even the pseudonym. Not written when no row named the user;
   - always, a `user.erased` SYSTEM event whose actor is the user the application announced as deleting (`AdminUserService` sets the transaction-local `qnop.erasing_actor` before the delete, after key-share locking the acting admin's row — attribution only, it authorises nothing; an unknown id, an admin deleted meanwhile, or the erased user itself becomes NULL. This actor is *app-asserted* attribution, like the actor of every other audit event: the database records whom the application named, it does not prove who asked) and whose detail is only `{redactionId}` (null when no row named the user). It never contains the erased user's id, so no redaction touches it; if the deleting admin is erased later, only its actor is pseudonymised like any other.
8. **Rows not yet sealed.** The seal now hashes the row as stored at commit instead of as inserted. A row written and redacted in the same transaction is sealed over its redacted content.
9. **Foreign key stays `ON DELETE RESTRICT`.** The trigger clears the actor before the key is checked, so RESTRICT only fires if the redaction did not run (e.g. its trigger was disabled). `SET NULL` would be a second write path outside the redaction context.
10. **Verification.** `AuditChainVerifier` treats a row carrying a `redaction_id` as follows: the `audit.chain.redacted` event with that id must exist, be sealed after the row, and be the *latest* redaction event listing the row; its listing must carry the row's position and stored `row_hash`, and a `contentHash` that the row's current content reproduces (Java re-implements the redaction canonical form independently, like the row form). A row listed as pending must reproduce its sealed hash *and* its content hash. A listed row that no longer carries a redaction id is reported too. Every such failure is a `BAD_REDACTION`; content edited after a redaction is therefore detected. The `prev_hash` link check across a redacted row is unchanged. A malformed redaction event, or a second one reusing an id, vouches for nothing but is *not* itself a finding — the first valid event per id wins — so no stray event can make verification fail permanently (the event is append-only and could never be removed).
11. **Concurrent writers.** `TeamMembershipAudit` — the writer that names a user in the detail rather than as actor — takes `FOR KEY SHARE` on the subject's `qnop_user` row before writing. A concurrent deletion therefore waits for it and then redacts its committed row; a writer that comes second finds the user gone and fails (`UserNotFoundException`, a 404) instead of writing their data. Actor references are covered by the foreign key the same way.
12. **Service and API.** `DELETE /admin/users/{id}` no longer answers `409 USER_HAS_AUDIT_HISTORY`; the code is retired (API description, UI message). The self-delete and last-admin guards are unchanged. The audit list shows an erased actor by its pseudonym (never as "System"; the system filter excludes it) and flags redacted entries (`redacted: true`).

**Consequences.**

- *What stays verifiable.* For a redacted row: its existence, position and links, its original hash (an anchored checkpoint of an earlier head still matches), and — through the content hash in the chained redaction event — its redacted content from the moment of redaction on. What is no longer verifiable is the *original* content: it is gone. That an erasure happened, when, and at whose request is itself chained (`audit.chain.redacted`, `user.erased`). This is the intended trade: GDPR requires the personal data to go, and "this row was rewritten by erasure X at time T" is the strongest statement the trail can still make.
- *Who can do what.* The deployment's privileges, not this design, decide whether anyone but the schema owner can `UPDATE audit_event` — the restricted application role of `docs/DEPLOYMENT.md` cannot, but that role split is a recommendation, and the default and the "owner credentials for migrations" setups keep `UPDATE`. For such a role the guards are the line of defence: a direct update, with or without self-chosen settings, is rejected, because the guard requires trigger depth and the private context, and only admits the exact pseudonymised form of the row for the user actually being deleted. What such a role *can* do is delete a user, which erases them by design and leaves the chained `audit.chain.redacted`/`user.erased` events. The schema owner can still bypass everything (disable triggers, write the context, insert matching events) — the 0040 consequence "does not prevent on its own" applies unchanged; a forged redaction does not change any stored hash, so it is visible as an `audit.chain.redacted`/`user.erased` pair that should be reconciled with the admin actions that explain it.
- *Coverage limits (not redacted).* Free text naming a person without their id (a review title in `review.deleted`, a setting value in `settings.updated`, a comment-like string); the user's name or e-mail outside an object whose `userId` is the user; ids embedded inside longer strings or used as JSON object keys; non-canonical id spellings (no hyphens, braces); detail written by writers that do not lock the user (today only `TeamMembershipAudit` names users in the detail; a new writer that does must take the same key-share lock). Audit writers must keep naming users by id with the snapshot name next to a `userId`.
- *Privacy trade-offs kept deliberately.* The redaction event lists which positions changed, so it reveals which rows concerned the erased user (an activity pattern, not an identity). One pseudonym per erasure keeps that user's rows linkable to each other within the trail — useful for reading the trail, and not linkable to the person.
- *Rollback.* The changeset rollback removes the path and restores the 0040 seal and update guard, but keeps `audit.chain.redacted` and `user.erased` reserved (no writer remains). Redacted rows keep their pseudonymised content; a 0040-era verifier recomputes them and reports each as `CONTENT_MISMATCH` from then on.
- *Cost.* Deleting a user scans `audit_event` once (a text search over the detail) and locks the rows it redacts; acceptable for an admin action. Two concurrent deletions touching the same row serialise on it. If the trail grows large, a trigram index or a column of referenced user ids would remove the scan.

**Future direction (Option B, not implemented).** Personal data could be kept outside the hash: audit rows would carry a stable pseudonymous subject key, the hash would cover that key, and a separate `audit_subject` mapping (key → user id, names) would hold the personal data. Erasure would delete the mapping row and leave every audit row byte-for-byte unchanged and fully verifiable. It needs a canonical-form version bump, a migration of every existing row and every writer and reader of `detail`; worth revisiting if erasures become frequent or full content verifiability after erasure becomes a requirement.

## Amendment (2026-11, #959): owner-only authorisation for the cascade and its tombstones

**Context.** The #928 amendment sanctioned an `audit_event` delete only for the document cascade, and admitted an `audit.chain.pruned` insert only from the tombstone trigger. Both checks read transaction-local session settings: the `BEFORE DELETE` trigger on `document` appended the ids to `qnop.audit_cascade_docs`, and the tombstone trigger switched `qnop.audit_writing_tombstone` on around its insert. Any session can set either setting. The other conditions (trigger depth, a `DOCUMENT` row whose document is already gone) still had to hold, but the authorising state itself was session-chosen. #952 had already moved the redaction path to owner-only state for exactly this reason; this applies the same pattern here.

**Decision.** Migration `0043-audit-prune-context`:

1. **Cascade marker in owner-only state.** `audit_cascade_context (txid, document_id)` holds one row per document the transaction is deleting, keyed by `txid_current()`. `document_mark_audit_cascade` is now `SECURITY DEFINER` (with `search_path` pinned) and writes it. `audit_event_cascade_sanctioned`, which both the row guard (`audit_event_reject_direct_delete`, unchanged) and the tombstone trigger call, reads it only through the read-only `SECURITY DEFINER` helper `audit_cascade_marked`. It is `VOLATILE` now, so it always sees the marker written earlier in the statement. The "document already gone" and trigger-depth conditions stay.
2. **Tombstone authorised as an exact announced event.** `audit_event_record_prune` computes the tombstone detail once, writes it to `audit_prune_context (txid, event_detail)`, inserts the event with exactly that detail, and deletes the context row. The insert guard admits an `audit.chain.pruned` row only from inside a trigger (`pg_trigger_depth() > 1`), only while that context exists, and only as exactly the announced event: `SYSTEM` scope, no document, no actor, and a detail equal to the context's. The redaction checks from #952 are carried over unchanged.
3. **Cleanup inside the transaction.** The context is cleared in the same statement that uses it. The tombstone trigger, a statement trigger on `audit_event` that PostgreSQL fires once after all of a statement's cascades, even when they removed no row, is the last reader of the markers. It deletes the markers of every document that is gone. A trigger on `document` cannot do this, because the cascade's statement trigger fires after `document`'s own. As a result:
   - several documents deleted in one statement share one tombstone;
   - a document recreated with the same id later in the transaction is unmarked, so it is protected again and marked afresh when deleted again;
   - a savepoint rolled back takes its markers with it, because they are ordinary rows and `txid_current()` is the top-level id inside a subtransaction.
4. **Privileges.** Every privilege on both tables is revoked from `PUBLIC` and from every role that a default-privileges rule granted it to. `docs/DEPLOYMENT.md` adds them to the tables that must never be granted to the application role. The session settings are no longer read anywhere.
5. **Rollback.** The changeset rollback (`0043-audit-prune-context-rollback.sql`) restores the 0040 marker, sanction check and tombstone writer and the 0042 insert guard, and then drops the helpers and the two tables. That brings back the setting-based authorisation it replaced. It is exercised once in `AuditPruneGuardIT`.

**Consequences.**

- *Prevents* (for any role that does not own the schema): choosing the cascade marker or the tombstone switch per session. A session-set `qnop.audit_cascade_docs` sanctions no delete, and a session-set `qnop.audit_writing_tombstone` admits no tombstone, not even from inside a trigger. The restricted application role cannot write either table, yet it still deletes a review: its audit rows cascade away, a tombstone is written, and the chain verifies.
- *Unchanged:* the verifier and `AuditChainTombstone` (the tombstone format is identical), the review-deletion and purge services, and the 0040 statement that the schema owner can still bypass everything (write the context, disable triggers). Detection of that still relies on the external checkpoint.
- *Edge case, fails closed:* a user-defined trigger that deletes documents from inside another document deletion could spend an outer statement's marker before the outer cascade has run. That outer delete would then be refused, never silently allowed. No qnop trigger does this.
